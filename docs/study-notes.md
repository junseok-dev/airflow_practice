# 데이터 전처리 학습 노트

이 문서는 OULAD 전처리 작업을 하면서 공부해야 할 개념과, 실무에서 알아두면 좋은 판단 기준을 정리한 학습 노트입니다.

## 1. 데이터 전처리는 무엇인가

데이터 전처리는 원본 데이터를 분석이나 서비스에서 사용할 수 있는 형태로 바꾸는 과정입니다.

원본 데이터는 보통 바로 쓰기 어렵습니다.

- 파일이 여러 개로 나뉘어 있음
- 컬럼 이름과 의미를 먼저 이해해야 함
- 결측치가 있음
- 같은 의미의 데이터가 여러 테이블에 흩어져 있음
- 날짜, 숫자, 문자열 타입이 섞여 있음
- 데이터 크기가 너무 커서 한 번에 읽기 어려움

그래서 전처리는 보통 다음 순서로 진행합니다.

```text
원본 데이터 확인
-> 컬럼 의미 파악
-> 결측치/이상치 확인
-> 필요한 파일 조인
-> 타입 변환
-> 집계
-> 지표 계산
-> 분석/대시보드용 데이터 생성
```

## 2. Raw, Processed, Mart의 차이

프로젝트에서 데이터를 세 단계로 나누는 이유를 이해해야 합니다.

### Raw

원본 데이터입니다.

```text
data/raw/
```

특징:

- 다운로드한 그대로 보관
- 가능하면 수정하지 않음
- 다시 검증할 때 기준이 됨
- 용량이 크면 Git에 올리지 않음

### Processed

전처리된 중간 데이터입니다.

```text
data/processed/
```

특징:

- 결측치 처리, 조인, 타입 변환이 어느 정도 끝난 데이터
- 사람이 열어서 검증하기 좋음
- 다음 단계 계산의 재료가 됨

### Mart

서비스나 대시보드가 바로 쓰는 최종 데이터입니다.

```text
data/mart/
```

특징:

- FastAPI나 React가 바로 읽기 좋은 형태
- KPI 카드, 차트, 테이블에 맞게 가공됨
- 보통 JSON, CSV, DB 테이블 형태로 저장

실무에서는 이 세 단계를 나누는 습관이 중요합니다. 그래야 문제가 생겼을 때 어느 단계에서 잘못됐는지 추적할 수 있습니다.

## 3. 조인이 중요한 이유

실제 데이터는 한 파일에 모든 정보가 들어있지 않습니다.

OULAD도 마찬가지입니다.

```text
studentInfo.csv
-> 교육생 기본 정보

studentRegistration.csv
-> 등록일, 철회일

studentAssessment.csv
-> 교육생별 평가 점수

assessments.csv
-> 평가 마감일, 평가 가중치

studentVle.csv
-> 교육생별 학습 활동 로그
```

각 파일을 연결해야 의미 있는 분석이 가능합니다.

예를 들어 평가 지연 제출 여부를 계산하려면 두 파일이 필요합니다.

```text
studentAssessment.csv
-> 교육생이 언제 제출했는지

assessments.csv
-> 평가 마감일이 언제인지
```

그래서 다음처럼 조인합니다.

```text
studentAssessment + assessments
-> id_assessment 기준 조인
-> 제출일과 마감일 비교 가능
```

실무에서 조인할 때는 반드시 확인해야 할 것이 있습니다.

- 조인 키가 맞는가?
- 조인 후 행 수가 예상보다 늘거나 줄지 않았는가?
- 중복 키 때문에 데이터가 폭증하지 않았는가?
- left join, inner join 중 어떤 방식이 맞는가?

## 4. 결측치 처리에서 중요한 점

결측치는 값이 비어 있는 데이터입니다.

OULAD에서는 결측치가 빈 값뿐 아니라 `?`로도 들어있습니다.

그래서 이 프로젝트에서는 다음 값을 결측치로 봅니다.

```text
""
"?"
```

결측치를 무조건 삭제하면 안 됩니다.

예를 들어:

```text
date_unregistration이 비어 있음
-> 철회하지 않았다는 의미일 수 있음
```

반대로:

```text
score가 비어 있음
-> 평가 점수가 없으므로 평균 계산에서 제외해야 함
```

즉 결측치는 컬럼의 의미에 따라 다르게 처리해야 합니다.

실무에서 자주 쓰는 기준:

- 의미 있는 결측인지 확인
- 삭제할지, 0으로 채울지, 평균으로 채울지 결정
- 결측 여부 자체를 새로운 feature로 만들 수 있는지 판단
- 처리 기준을 문서에 남김

## 5. 집계란 무엇인가

집계는 여러 행을 하나의 기준으로 묶어 요약하는 것입니다.

예를 들어 `studentVle.csv`에는 교육생의 학습 활동 로그가 매우 많이 들어 있습니다.

하지만 대시보드에서는 개별 로그 전체보다 이런 값이 더 필요합니다.

```text
교육생별 총 클릭 수
교육생별 활동 일수
교육생별 주차별 클릭 수
```

그래서 다음 기준으로 묶습니다.

```text
code_module
code_presentation
id_student
week
```

그리고 계산합니다.

```text
sum_click 합계
date 고유 개수
```

이렇게 하면 로그 데이터가 대시보드 차트용 데이터로 바뀝니다.

## 6. 큰 파일을 다룰 때 주의할 점

`studentVle.csv`는 약 432.81 MB, 10,655,280행입니다.

이런 파일을 무조건 한 번에 읽으면 메모리를 많이 사용합니다.

그래서 이 프로젝트에서는 `chunksize`를 사용했습니다.

```python
pd.read_csv("studentVle.csv", chunksize=500_000)
```

의미:

```text
한 번에 50만 행씩 읽고
각 chunk를 처리한 뒤
마지막에 합친다
```

실무에서 큰 데이터를 다룰 때 알아두면 좋은 방법:

- 필요한 컬럼만 읽기: `usecols`
- chunk 단위로 읽기: `chunksize`
- 중간 결과를 파일로 저장하기
- DB에서 집계한 뒤 가져오기
- parquet 같은 효율적인 포맷 사용 검토

## 7. 정규화가 필요한 이유

평가 점수는 보통 0~100점입니다.

하지만 클릭 수는 사람마다 범위가 크게 다릅니다.

예:

```text
학생 A: 20 클릭
학생 B: 2,000 클릭
학생 C: 50,000 클릭
```

이 값을 그대로 점수 계산에 넣으면 클릭 수가 너무 큰 영향을 줍니다.

그래서 클릭 수를 0~100 범위로 바꾸는 정규화를 합니다.

이 프로젝트에서는 95분위 값을 기준으로 사용했습니다.

```text
상위 5%의 매우 큰 값을 기준 밖으로 잘라내고
나머지를 0~100 점수로 변환
```

왜 평균이나 최대값이 아니라 95분위를 썼나?

- 최대값은 극단값의 영향을 너무 많이 받음
- 평균은 분포가 치우쳐 있으면 기준으로 약할 수 있음
- 95분위는 상위권 활동량을 기준으로 하되 극단값 영향을 줄임

## 8. 지표 설계는 정답이 아니라 가설이다

이 프로젝트의 종합 역량 점수는 다음 기준으로 만들었습니다.

```text
종합 역량 점수 =
평가 성취도 45%
+ 학습 참여도 35%
+ 학습 성실도 20%
```

이건 정답이 아니라 첫 번째 가설입니다.

왜냐하면 실제 교육 현장에서는 다음 질문을 더 확인해야 하기 때문입니다.

- 평가 점수가 정말 역량을 잘 대표하는가?
- 클릭 수가 많으면 학습을 잘했다고 볼 수 있는가?
- 제출률과 지연 제출률의 비중은 적절한가?
- 과정별 난이도 차이를 보정해야 하는가?
- 중도 철회자를 무조건 고위험으로 볼 것인가?

실무에서 지표를 만들 때 중요한 태도:

- 처음부터 완벽한 지표를 만들려고 하지 않기
- 기준을 명확히 문서화하기
- 결과 분포를 확인하기
- 현업 피드백을 받아 기준을 조정하기

## 9. 위험도 분류는 왜 조심해야 하나

위험 교육생 분류는 유용하지만 조심해야 합니다.

현재 기준:

```text
medium:
- 종합 역량 점수 < 65
- 또는 평가 점수 < 50
- 또는 학습 참여 점수 < 35

high:
- 수강 철회
- 또는 종합 역량 점수 < 50
- 또는 평가 점수 < 40 이면서 학습 참여 점수 < 30
```

주의할 점:

- 위험도는 낙인이 아니라 지원이 필요한 신호로 봐야 함
- 기준이 너무 엄격하면 대부분이 위험으로 분류될 수 있음
- 기준이 너무 느슨하면 실제 도움이 필요한 사람을 놓칠 수 있음
- 분류 결과를 차트로 보고 기준을 조정해야 함

실무에서는 위험도 기준을 혼자 정하지 않고, 교육 담당자나 현업 담당자와 함께 조정합니다.

## 10. 전처리 결과는 반드시 검증해야 한다

전처리 스크립트가 실행된다고 끝이 아닙니다.

항상 확인해야 합니다.

- 생성된 파일이 있는가?
- 행 수가 예상과 맞는가?
- 평균 점수가 이상하지 않은가?
- 결측치가 예상대로 처리됐는가?
- 조인 후 데이터가 사라지거나 중복 폭증하지 않았는가?
- 대시보드에 필요한 컬럼이 모두 있는가?

이 프로젝트에서는 `docs/transform.md`에 전처리 산출물과 요약 지표를 기록했습니다.

## 11. 실무에서 좋은 전처리 코드의 특징

좋은 전처리 코드는 단순히 결과만 만드는 코드가 아닙니다.

좋은 전처리 코드는:

- 입력 경로와 출력 경로가 명확함
- 단계별 함수가 나뉘어 있음
- 중간 산출물을 저장함
- 큰 파일을 고려함
- 결측치 기준이 명확함
- 결과를 문서로 남김
- 다시 실행해도 같은 결과가 나옴

이 프로젝트의 `transform_competency.py`도 이 흐름을 따르려고 구성했습니다.

## 12. 지금 코드에서 더 개선할 수 있는 점

현재 전처리는 첫 번째 버전입니다.

개선할 수 있는 점:

- 위험도 기준을 더 정교하게 조정
- 과정별 난이도 차이 보정
- 클릭 수 대신 활동 유형별 가중치 반영
- 평가 유형별 가중치 세분화
- `studentVle.csv` 처리 결과를 parquet으로 저장
- 단위 테스트 추가
- Airflow DAG로 전처리 자동화
- FastAPI에서 큰 JSON을 바로 읽는 대신 페이지네이션 적용

## 13. 이 프로젝트에서 꼭 가져가야 할 공부 포인트

- 데이터셋 설명 파일을 먼저 읽는 습관
- 원본 데이터와 가공 데이터를 분리하는 습관
- 조인 키를 먼저 확인하는 습관
- 결측치가 어떤 의미인지 고민하는 습관
- 대용량 파일은 chunk로 처리하는 방법
- 지표는 가설이며 조정 가능하다는 관점
- 전처리 결과를 문서로 남기는 습관
- 프론트엔드가 쓰기 좋은 형태로 mart 데이터를 만드는 감각

## 14. 면접이나 실무 대화에서 설명하는 방식

이 프로젝트를 설명할 때는 이렇게 말할 수 있습니다.

```text
OULAD 학습 로그 데이터를 활용해 교육생 역량 대시보드용 데이터를 만들었습니다.
원천 CSV를 raw 영역에 보관하고, 평가 데이터와 학습 활동 데이터를 조인/집계해
processed 데이터를 생성했습니다.
이후 평가 성취도, 학습 참여도, 학습 성실도를 조합해 종합 역량 점수를 만들고,
위험 교육생을 분류한 mart JSON을 생성했습니다.
이 mart 데이터는 FastAPI를 통해 React 대시보드에서 사용할 예정입니다.
```

핵심 키워드:

- raw / processed / mart
- join key
- missing value
- aggregation
- normalization
- competency score
- risk level
- dashboard API
